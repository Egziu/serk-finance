# SERK Finance ERP — 0.2.1-rc1 repair release

This archive contains the corrected source, rebuilt frontend, forward database migrations, regression tests, and current validation evidence. Start with this file and `serk-finance/REPAIR_VALIDATION.md`.

This is a release candidate. It has **not** been approved for live finance: the Go compiler, native PostgreSQL, Docker, and a local browser engine were unavailable; image/dependency scans and production infrastructure acceptance were not run. The included SQL and frontend checks do not replace those acceptance gates.

## Main corrections

- Posted journals and their lines/dimensions are immutable, including SYSTEM entries. Runtime database users have no direct financial write grants.
- Module journals start as drafts and pass the kernel's validation, numbering, submission, independent approval, posting, reversal, and idempotency controls.
- Integrity checks compare current posted contents with their final audited snapshots. Module posting stops if reconciliation fails.
- Invoice, bill, tax, payroll, and stock values use exact numeric arithmetic and string money values over the API.
- Sales post cost of sales and inventory value; purchases and approved stock openings update both quantities and value. Reservations prevent overselling. Moving weighted cost is fixed at submission, and movements respect accounting-date order.
- Payments require their own independent approval. Pending payments/reversals can be voided and prepared again without reusing an old financial operation.
- Payroll records dated payruns and payslips, applies an approved policy for the selected frequency, and prevents duplicate/overlapping processing of one period.
- Salary/document reads require the relevant module permission. Company and branch boundaries also apply at the database level.
- Authenticator replacement/removal requires password and current-factor verification, and revokes all sessions. Mandatory MFA cannot be disabled.
- Balance-sheet categories are disjoint. Dashboard figures include posted journals only and retain exact money values.

## Run locally on Ubuntu

Required: Go 1.27.1, Node.js 22 or newer, Python 3; Docker Compose is optional for embedded development and required for the container path.

From the outer `serkFinanceERP` folder:

```bash
./setup-ubuntu.sh
./run.sh dev
```

Alternatively, `./run.sh docker` initializes a local development stack. These commands are development launchers; use the hardened release manifest for staging/production.

The application opens at `http://localhost:8080`. Embedded development resets its synthetic data when stopped. Docker development credentials are generated by `serk-finance/scripts/init-local.py` and written to a private local sign-in file. No fixed passwords or MFA key are included in this release.

## Configure before financial use

1. Create the company's chart and fiscal periods. Configure explicit account mappings and the allowed cash/bank accounts in the relevant workspace. Choose dedicated accounts for receivables, payables, inventory, tax, and payroll. Configuration changes do not change the control account recorded on an existing document.
2. Create customers/vendors, catalog items, and employees. Product items need inventory and cost-of-sales account mappings. Employees need a branch, salary per pay period, and frequency.
3. Use a stock-opening document for opening quantities/value; obtain independent approval. Direct quantity-only opening entries are rejected.
4. A configuration manager enters payroll brackets, offsets, pension percentages, frequency, and effective dates. A different configuration manager approves the policy. No statutory tax/pension rates are assumed. Obtain current accountant/localization approval for actual policies.
5. The preparer saves a document, reviews it, and submits it. A different authorized person approves and posts it. Payments and reversals have their own review and independent approval. Review the document preview before authorizing an action.

Module preparers need the module's read/manage permissions, ledger read, audit read for reconciliation, and journal create/submit permissions. Approvers also need journal approve/post with suitable limits. Configuration permissions are separately controlled.

The local Docker seed includes an administrator, accountant, finance approver, and restricted configuration reviewer so payroll rules can be reviewed by a second identity. Use distinct real people and credentials for production.

The release gate includes the repaired full-schema SQL suite and SQL upgrade-preservation checks, in addition to the original Go, browser, dependency, and upgrade gates. Do not accept a failed, blocked, filtered, or stale run. Also complete verified TLS/secrets/MFA setup, target capacity tests, image/dependency scans, backup restore/PITR, and independent accounting/security acceptance.

## Upgrading an existing database

Read `serk-finance/UPGRADE_FROM_ORIGINAL.md` first. Preserve a verified backup and stop the application during migration. The original numbered migrations 001–036 are unchanged; a narrowly scoped operator preparation step enables the legacy 033 migration on populated databases, and later migrations remove that temporary access policy.

Invalid historical account references, zero/invalid salaries, or quantity-only inventory balances cause migration to fail rather than inventing corrections. Posted records whose old contents were never captured by the audit trail also require accounting reconciliation. This repair does not fabricate historical audit evidence or rewrite existing posted amounts to make an integrity indicator green.

Archive checksums are in the outer and inner `SHA256SUMS` files. Existing source-version/design documents are labelled historical references; the current release notes and validation record are authoritative.
